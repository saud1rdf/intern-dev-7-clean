# Git Basics & Branching Strategies

## Overview & The Why (لماذا هذا المفهوم حيوي؟)
In modern, high-availability enterprise environments, systems must track modifications with absolute mathematical certainty, auditability, and historical integrity. Version control is not merely a backup tool; it is the fundamental ledger of software state.

Without a rigorous and auditable history:
1. **Regression Profiling (git bisect)**: Isolating production bugs under load becomes a manual, slow search. Utilizing proper git mechanics permits binary searches on the commit graph to detect error commits in O(log N) iterations.
2. **Deterministic Releases**: Automations (Semantic Versioning) cannot auto-generate Changelogs or compute precise semver increments if commit messages are unstructured or loose (squashing is helpful but structured headers are essential).
3. **Reproducibility**: Compliance requirements mandate an untainted DAG (Directed Acyclic Graph) of commit signatures matching deployed container hashes.

---

## Key Concepts (ا#لمفاهيم الأساسية)

- **The Git Object Database**: In Git, all contents are stored as content-addressable objects under three main structural classes:
  - **Blobs**: Bare file content representation, excluding metadata or path hashes.
  - **Trees**: Directional directories mapping filenames to nested trees or direct blobs.
  - **Commits**: Cryptographically signed nodes identifying author stamps, timestamps, parent hashes, and pointers to root directory trees.
- **DAG (Directed Acyclic Graph)**: Branches are not isolated directories; they are loose references (pointer files containing a single SHA-1 hash) shifting along historical commit vertices on an immutable graph.
- **Trunk-Based Development**: Instead of maintaining highly concurrent, long-lived feature branches which yield extreme integration blockages (merge conflicts/friction), high-velocity teams rely on short-lived branches (1-2 days) merged frequently into the primary trunk (`main`), protected by feature flags to decouple releases from deployments.
- **Conventional Commits**: A structured commit format (`<type>(<scope>): <description>`) that serves as programmatic metadata.

---

# REST API Integration & Defensive Validation

## Overview & The Why (لماذا هذا المفهوم حيوي؟)
In modern web architectures, API integrations are the critical point of contact between your secure, structured frontend application and the untrusted external network. 

Any frontend that treats API returns as loosely-typed arrays or objects is prone to major failures:
1. **Silent Schema Drift**: Downstream third-party APIs can undergo schema shifts without signaling warnings, emitting missing attributes or unexpected types. If left unchecked, this causes client-side UI failure at runtime.
2. **Exposing Secrets**: Fetching keys directly from browser code exposes private API credentials, developer endpoints, and database connection strings to client-side environments.
3. **Transient Drops**: Network drops and transient glitches occur frequently. Applications without programmatic fallback loops and exponential retry logic yield poor user experience.

---

## Key Concepts (المفاهيم الأساسية)

- **Defensive API Gateways**: Every payload received from an external system must be verified at the network boundary before passing into state structures.
- **Runtime Type Enforcement**: While TypeScript ensures type safety during compilation, compile-time interfaces disappear in browser runtime. Runtime validation (using schema checkers like Zod) is required to ensure data matches expected shapes.
- **API Proxy Routing**: Querying private database endpoints or key-driven systems from secure serverless or server configurations preserves client confidentiality.
- **Idempotency & HTTP Verbs**: Standardizing CRUD actions (GET, POST, PUT, PATCH, DELETE) ensures safe, repeatable requests.

---

## Production-Grade Code (الشيفرة البرمجية الإنتاجية)

### 1. Robust API Client Wrapper with Exponential Retry Backoff (`lib/api-client.ts`)
This class provides a reliable endpoint fetching structure, parsing formats safely, and handling server throttling (status 429) or database connection dropouts with custom retries:

```typescript
import { z } from 'zod';

export class APIClientError extends Error {
  constructor(
    public status: number,
    public payload: unknown,
    message?: string
  ) {
    super(message || `API HTTP failure with response status: ${status}`);
    this.name = 'APIClientError';
  }
}

interface RequestOptions extends RequestInit {
  maxRetries?: number;
  baseBackoffMs?: number;
}

export async function defensiveFetch<TSchema extends z.ZodTypeAny>(
  url: string,
  schema: TSchema,
  options: RequestOptions = {}
): Promise<z.infer<TSchema>> {
  const { maxRetries = 3, baseBackoffMs = 500, ...fetchConfig } = options;
  let attempt = 0;

  while (attempt < maxRetries) {
    try {
      const response = await fetch(url, {
        ...fetchConfig,
        headers: {
          'Content-Type': 'application/json',
          ...fetchConfig.headers,
        },
      });

      // Catch negative response statuses immediately
      if (!response.ok) {
        let errorPayload: unknown;
        try {
          errorPayload = await response.json();
        } catch {
          errorPayload = await response.text();
        }
        throw new APIClientError(response.status, errorPayload);
      }

      const rawData = await response.json();

      // Enforce schema validation at runtime entry
      const validationResult = schema.safeParse(rawData);
      if (!validationResult.success) {
        console.error('[REST_CLIENT_SCHEMA_DRIFT] validation details failed:', validationResult.error.format());
        throw new Error('Integrity validation failed: Payload signature is corrupted');
      }

      return validationResult.data;

    } catch (error) {
      attempt++;
      if (attempt >= maxRetries) {
        throw error;
      }

      // Exponential wait: attempt 1 = 1000ms, attempt 2 = 2000ms...
      const delay = baseBackoffMs * Math.pow(2, attempt);
      console.warn(`[API_RETRIER] Attempt ${attempt} failed. Retrying in ${delay}ms... Details:`, error);
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }

  throw new Error('Request pipeline terminated: too many validation failures');
}

TypeScript

import { NextRequest, NextResponse } from 'next/server';
import { z } from 'zod';

const incomingQuerySchema = z.object({
  department: z.string().min(1).default('engineering'),
  limit: z.coerce.number().min(1).max(100).default(20),
});

export const targetResponseSchema = z.array(
  z.object({
    id: z.string().uuid(),
    fullName: z.string(),
    userEmail: z.string().email(),
    isActive: z.boolean(),
  })
);

export async function GET(request: NextRequest) {
  try {
    const { searchParams } = new URL(request.url);

    // 1. Defensively validate query parameters from incoming search requests
    const query = incomingQuerySchema.parse({
      department: searchParams.get('department') || undefined,
      limit: searchParams.get('limit') || undefined,
    });

    const secureToken = process.env.API_GATEWAY_JWT_TOKEN;
    const internalEndpoint = `${process.env.INTERNAL_SERVICE_API}/v1/users?dept=${query.department}&limit=${query.limit}`;

    if (!secureToken || !process.env.INTERNAL_SERVICE_API) {
      return NextResponse.json(
        { success: false, message: 'Server variables must be correctly declared in runtime environment' },
        { status: 500 }
      );
    }

    // 2. Perform secure backend API query with server authorization
    const rawData = await fetch(internalEndpoint, {
      headers: {
        'Authorization': `Bearer ${secureToken}`,
      },
    }).then((res) => {
      if (!res.ok) throw new Error(`Upstream system returned error status ${res.status}`);
      return res.json();
    });

    // 3. Enforce contract integrity before sending to client
    const verifiedUsersList = targetResponseSchema.parse(rawData);

    return NextResponse.json({
      success: true,
      data: verifiedUsersList,
    });

  } catch (error) {
    if (error instanceof z.ZodError) {
      return NextResponse.json(
        { success: false, message: 'Schema validation mismatched', errors: error.flatten() },
        { status: 400 }
      );
    }

    console.error('[PROXY_ROUTE_EXCEPTION]', error);
    return NextResponse.json(
      { success: false, message: 'Upstream gateway failed to resolve query request' },
      { status: 502 }
    );
  }
}

# GraphQL Integration with Apollo Client

## Overview & The Why (لماذا هذا المفهوم حيوي؟)
GraphQL permits clients to query and aggregate disparate systems through an unified semantic gateway. Unlike REST, which often suffers from over-fetching unnecessary fields or under-fetching related records, GraphQL specifies response expectations down to the individual attribute layer.

However, unchecked or unoptimized GraphQL setups introduce severe performance issues:
1. **Normalized Cache Drift**: If queries do not share unique record identifiers (`__typename` and `id`), duplicate database rows yield conflicting client-side views.
2. **Server Overhead (N+1 Queries)**: Traversing un-cached nested structures under heavy relational loads can freeze production transactional tables.
3. **Loss of Compile Safe Types**: Failing to tie client-side query documents (AST) to code generation steps allows front-end variables to mismatch server schemas without compiler warnings.

---

## Key Concepts (المفاهيم الأساسية)

- **Unified Schema Gateway**: Merging disjointed microservice layers into cohesive semantic models, allowing clients to traverse properties within a single request.
- **Normalized InMemoryCache**: Keying elements unique to their entity signatures, facilitating instant updates across views whenever mutation calls execute.
- **Link Processing Pipeline**: Directing queries through configurable middleware layers before sending payloads to network hosts.
- **WebSocket Subscriptions**: Running long-lived connection tunnels alongside HTTP pipes to stream messages asynchronously.

---

## Production-Grade Code (الشيفرة البرمجية الإنتاجية)

// Validate system endpoint values safely prior to initialization
const configSchema = z.string().url();
const graphQLEndpoint = configSchema.parse(
  process.env.NEXT_PUBLIC_GRAPHQL_API_URL || 'http://localhost:3000/api/graphql'

// 1. Error Link Interceptor to handle unified API errors
const errorLink = onError(({ graphQLErrors, networkError }) => {
  if (graphQLErrors) {
    graphQLErrors.forEach(({ message, locations, path }) => {
      console.error(
        `[GraphQL_SCHEMA_ERROR] Message: ${message}, Path: ${path}`
      );
    });
  }
  if (networkError) {
    console.error(`[NETWORK_TRANSPORT_FAILURE] Failure details: ${networkError.message}`);
  }
});

// 2. Auth Link to inject enterprise context parameters
const authLink = new ApolloLink((operation, forward) => {
  const token = typeof window !== 'undefined' ? localStorage.getItem('token') : null;
  
  operation.setContext(({ headers = {} }) => ({
    headers: {
      ...headers,
      authorization: token ? `Bearer ${token}` : '',
    },
  }));
  
  return forward(operation);
});

const httpLink = new HttpLink({
  uri: graphQLEndpoint,
});

// 3. Centralized Apollo Client with optimized pagination cache policy
export const apolloClient = new ApolloClient({
  ssrMode: isServer,
  link: from([errorLink, authLink, httpLink]),
  cache: new InMemoryCache({
    typePolicies: {
      Query: {
        fields: {
          // Stable offset-limit pagination policy to append records safely
          users: {
            keyArgs: false,
            merge(existing = [], incoming) {
              return [...existing, ...incoming];
            },
          },
        },
      },
    },
  }),

# React High-Performance State Architecture

## Overview & The Why (لماذا هذا المفهوم حيوي؟)
React’s virtual DOM paradigm simplifies interface code by automatically computing view shifts based on state modifications. 

However, in large-scale systems (like dashboards tracking real-time telemetry inputs), unoptimized state patterns lead to sluggish rendering and unstable codebases:
1. **Cascading Re-Renders**: Storing massive, unseparated arrays inside high-level Context engines triggers full tree rebuilds across hundreds of components whenever a single attribute updates.
2. **Lost Navigation States**: Relying exclusively on temporary client-side memory resets filters, tables, and pagination states whenever a user refreshes their browser. This breaks sharing capability.
3. **Stale Closure Closures**: Incorrect setup of Hook dependency arrays causes variables to retain outdated scopes, producing subtle, hard-to-track bugs.

---

## Key Concepts (المفاهيم الأساسية)

- **Reconciliation Optimization**: Controlling render trees selectively using tools like memoization, stable references, and proper memo boundaries.
- **State Taxonomy Boundaries**: Isolating state into: Local UI State (isolated within a component), Shared Global State (cross-component panels), Server State (cached API data), and URL State (persistent coordinates).
- **Split Context Pattern**: Splitting a Context Provider into separate State and Dispatch context arrays to completely prevent unnecessary component re-renders.
- **Immutability Principle**: Ensuring React state is never mutated directly, as React relies on reference changes to trigger reconciliation safely.

---

## Production-Grade Code (الشيفرة البرمجية الإنتاجية)

### 1. High-Performance Split Context Pattern (`providers/UnifiedStateProvider.tsx`)
This pattern separates state context values from the dispatch context. This ensures that components only reading static states do not re-render when write handlers fire:

```tsx
'use client';

import React, { createContext, useContext, useReducer } from 'react';

interface AppState {
  theme: 'light' | 'dark';
  sidebarOpen: boolean;
}

type Action =
  | { type: 'TOGGLE_THEME' }
  | { type: 'SET_SIDEBAR'; payload: boolean };

const initialState: AppState = {
  theme: 'light',
  sidebarOpen: false,
};

// 1. Create separate contexts to isolate state from dispatcher triggers
const StateContext = createContext<AppState | undefined>(undefined);
const DispatchContext = createContext<React.Dispatch<Action> | undefined>(undefined);

function stateReducer(state: AppState, action: Action): AppState {
  switch (action.type) {
    case 'TOGGLE_THEME':
      return { ...state, theme: state.theme === 'light' ? 'dark' : 'light' };
    case 'SET_SIDEBAR':
      return { ...state, sidebarOpen: action.payload };
    default:
      return state;
  }
}

export function UnifiedStateProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(stateReducer, initialState);

  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}>
        {children}
      </DispatchContext.Provider>
    </StateContext.Provider>
  );
}

// 2. Export isolated hooks with boundaries
export function useAppState() {
  const context = useContext(StateContext);
  if (!context) {
    throw new Error('useAppState must be used within UnifiedStateProvider');
  }
  return context;
}

export function useAppDispatch() {
  const context = useContext(DispatchContext);
  if (!context) {
    throw new Error('useAppDispatch must be used within UnifiedStateProvider');
  }
  return context;
}

'use client';

import { useRouter, useSearchParams, usePathname } from 'next/navigation';
import { useCallback, useMemo } from 'react';

export function useURLQueryState<T extends string>(
  paramName: string,
  defaultValue: T
): [T, (newValue: T) => void] {
  const router = useRouter();
  const searchParams = useSearchParams();
  const pathname = usePathname();

  // Parse current coordinate safely
  const activeValue = useMemo(() => {
    return (searchParams.get(paramName) as T) || defaultValue;
  }, [searchParams, paramName, defaultValue]);

  const updateValue = useCallback((newValue: T) => {
    const params = new URLSearchParams(searchParams.toString());
    
    if (newValue === defaultValue) {
      params.delete(paramName);
    } else {
      params.set(paramName, newValue);
    }
    
    // Smooth, non-blocking history push transition
    router.push(`${pathname}?${params.toString()}`, { scroll: false });
  }, [router, searchParams, pathname, paramName, defaultValue]);

  return [activeValue, updateValue];
}

# Next.js App Router & Server Architecture

## Overview & The Why (لماذا هذا المفهوم حيوي؟)
The Next.js App Router introduces a fundamental shift in how web applications are rendered and delivered. By moving components to the server by default (React Server Components), the framework reduces client-side JavaScript delivery to zero for pure presentational sections.

Understanding this architecture is critical for several key reasons:
1. **Optimal Initial Web Hydration**: Server components fetch data directly from co-located databases and assets, outputting finished HTML trees to client browsers. This optimizes Core Web Vitals (LCP, FID) and maximizes SEO indexability.
2. **Unified Data Mutating Pipeline**: Server Actions handle database writes securely in a single location, reducing network overhead.
3. **Resilient Data Security**: Access tokens, secret gateway credentials, and system settings remain safely on the server side, with no exposure to browser client inspectors.

---

## Key Concepts (المفاهيم الأساسية)

- **React Server Components (RSC)**: Server-side components that fetch data directly and render markup on the server, sending zero client-side JavaScript.
- **Universal Code Splitting**: Marking interactive components with the `'use client'` directive to define specific client-side bundle boundaries.
- **Hydration Coordination**: Aligning server-rendered DOM with client-rendered DOM cleanly, avoiding date or browser-API mismatches.
- **Server Actions with Progressive Enhancement**: Secure, server-side forms that execute successfully even if the client's Javascript thread is blocked or loading.

---

# Unit, E2E Testing & Structured Logging

## Overview & The Why (لماذا هذا المفهوم حيوي؟)
In modern high-availability applications, testing and observability are tightly integrated. Tests ensure that your application remains reliable *before* deployment, while telemetry and structured logging observe and monitor systems *after* deployment.

Relying on loose testing patterns or basic `console.log` statements introduces significant production risks:
1. **Console API Bottlenecks**: Raw `console.log` statements blocked in single-threaded runtimes (like Node.js) cause synchronous disk I/O, which can severely degrade API throughput under heavy traffic.
2. **Schema and Layout Regressions**: Manual QA cannot consistently catch visual errors, broken layout boundaries, and form routing flaws across hundreds of different UI routes.
3. **Trace Fragmentation**: When API requests fail across distributed microservices, tracing root causes is nearly impossible without standardized log attributes linked by a single Correlation trace ID.

---

## Key Concepts (المفاهيم الأساسية)

- **Unit and Integration Isolation**: Testing algorithms and pure calculation modules strictly, avoiding external network interfaces through mock objects.
- **Component Interaction (RTL)**: Testing user behavior patterns in components by querying accessible roles (ARIA), rather than targeting fragile CSS classes.
- **End-to-End Simulation (Playwright)**: Verifying complex multi-page scenarios in real browser engines to trace layouts, session cookies, and database syncing.
- **Structured JSON Logs**: Recording application events in standardized, machine-readable JSON format for instant querying in search backends (e.g. Datadog or ELK).

---

export function computeCompoundBilling(
  monthlyBase: number,
  taxRate: number,
  discountAmount: number
): number {
  if (monthlyBase < 0 || taxRate < 0 || discountAmount < 0) {
    throw new Error('Billing numbers must be non-negative parameters');
  }
  const computedTax = monthlyBase * taxRate;
  const grossValue = monthlyBase + computedTax;
  return Math.max(0, parseFloat((grossValue - discountAmount).toFixed(2)));
}

// Jest testing block
describe('computeCompoundBilling enterprise calculations', () => {
  it('should accurately apply tax rate and subtract flat discounts', () => {
    const result = computeCompoundBilling(100, 0.15, 20); // (100 + 15) - 20 = 95
    expect(result).toBe(95.00);

  it('should safely return zero if discount exceeds the total gross value', () => {
    const result = computeCompoundBilling(50, 0.10, 200); // (50 + 5) - 200 = -145 -> returns 0

  });
